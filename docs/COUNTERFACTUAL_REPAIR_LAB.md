# Counterfactual Repair Lab

Adds a fourth root-cause strategy that validates candidate corrections against the real
compiler instead of only ranking them heuristically, and folds that evidence into the
existing rule/ML ranking. It reuses the existing architecture end to end - no new patch
templates, no new compiler integration, no new sandboxing: every compile it performs is
the same `LanguageAdapter.check()` every other strategy already calls.

## Modules

- `compiler_engine/counterfactual/evaluator.py` - **Phase 2.** For each candidate line
  (already generated by the existing `localization.candidates`/`patches.generator`),
  applies each of `patches.generator.patches_for_line()`'s templates to a temporary copy of
  the source (`patches.generator.apply_edits`, which returns a new string - the caller's
  source is never touched) and compiles the copy with the real adapter. Records compiled
  y/n, which original diagnostics disappeared, which new ones appeared, edit size, timeout
  status and duration as a `PatchEvidence`/`LineEvidence` pair. Bounded by
  `max_lines` × `patches_per_line` (defaults 6×3, hard cap 12×6) so one request cannot
  spawn an unbounded number of compiler invocations. Never raises on a missing toolchain or
  a failed compile - both become ordinary `unvalidated`/`not_fixed` evidence.
- `compiler_engine/counterfactual/evidence_ranker.py` - **Phase 3.** Combines the existing
  rule score, the existing ML score (when available) and the evidence above into one
  ranked, *documented* heuristic (see the module docstring for the exact formula) - not a
  retrained model, not a calibrated probability. When more than one candidate line
  compiles, `ambiguous=True` and every verified line is listed rather than silently picking
  a winner.
- `compiler_engine/pipeline.py` - `DiagnosisEngine.diagnose(..., counterfactual=True)` is
  **opt-in** (default `False`, so every existing caller/test is byte-for-byte unaffected)
  and adds a `strategies.counterfactual` block alongside the existing
  `conventional`/`rule`/`ml` ones. It does not change `primary_strategy`/`root_cause_line`
  selection - those remain rule/ML as before.
- `backend/service.py` - `Service.counterfactual()` is a thin wrapper that calls
  `diagnose(..., counterfactual=True)` and 409s if the source has no syntax error to
  analyse. Routed as `POST /api/counterfactual` on both the stdlib server
  (`backend/simple_server.py`) and the FastAPI app (`backend/fastapi_app.py`).
- `benchmarks/runner.py` - **Phase 4.** `counterfactual_eval()` reports Top-1/Top-3/MRR,
  verified-repair-rate, false-correction-rate and average validation time, on the *same*
  bounded per-language sample set `suggestion_eval()` already uses (`_select_rows()`) -
  see `docs/KNOWN_LIMITATIONS.md` #11 for why this is a smaller n than the main benchmark.
- `frontend/src/App.tsx` (`RepairLab`/`CfCandidate`) - **Phase 5.** A panel in the existing
  IDE view: "Run Repair Lab" calls `/api/counterfactual` and lists every validated
  candidate with its diff, status, evidence notes and edit size; Accept/Reject reuse the
  existing `/api/patch/apply` flow and never modify the editor without an explicit click.

## Why it is opt-in

Counterfactual validation compiles code - unlike rule/ML ranking it is not free. Making it
the default on every `/api/diagnose` call would silently double-to-triple the number of
compiler invocations per request (and, in the benchmark, per held-out sample). Instead it
is a separate, explicit action (`POST /api/counterfactual`, or `counterfactual: true` on
`/api/diagnose`) so existing behaviour, performance and test assertions are unchanged
unless a caller asks for it.
